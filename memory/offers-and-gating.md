Logique de gating décidée (juin 2026). Voir [[business-model]], [[accounts-and-access]], [[admin-build-roadmap]].

**Mécanisme de verrouillage (décision A)** : chaque fonctionnalité porte UN tag « offre minimale » **dans le catalogue code** (`lib/shared/data/features_catalog.dart`, modèle `AppFeature`, champ `minPlan` ✅ AJOUTÉ juin 2026, défaut `'simple'`). Offres ordonnées : **Simple(0) < Pro(1) < Max(2)** (helper `planMeetsRequirement(current, required)` dans `lib/shared/widgets/plan_gate.dart` = source unique de la comparaison). Une feature s'affiche si `offre_école ≥ minPlan_feature`. Tags posés : **Pro** = messaging, liaison, parent_meetings, announcements, broadcast, fees_parent, fees_student, library, discipline, reports, certificates, archives, quiz ; **Max** = offline ; reste = simple. Les features universitaires/recherche restent `simple` (à gater par TYPE d'école plus tard, ≠ offre). Utilisé à 3 endroits prévus : **navigation** (cacher/griser), **hub/pages** (cadenas + upsell ✅ Features Hub affiche badge `🔒 Pro/Max` via `_PlanLockBadge`), **création de comptes** (rôles autorisés). Le gating des features = **logique métier app-level** (pas de la sécurité — la RLS isole déjà). SEULE la **limite d'élèves** a un garde-fou en base (trigger + `school_can_add_student`).

**Limite d'élèves — état (juin 2026)** : vérif app-side via `canAddStudent()` à l'ouverture ET au save du formulaire d'inscription (`users_page.dart`). Bug corrigé (`20260618_fix_can_add_student.sql`) : `school_can_add_student` bloque désormais quand AUCUN abonnement (avant : NULL limit = illimité par erreur, distinct du vrai Max illimité). ⏳ Reste le garde-fou trigger sur INSERT users (ROADMAP A3, Phase 4 non faite). Bannière d'expiration globale dans les 2 shells (`SubscriptionAlertBanner`, gatée admin/staff sur mobile).

**Double étiquette par feature** : (1) **Offre** Simple/Pro/Max + (2) **Maturité** `available`/`planned` (déjà dans le catalogue via `FeatureStatus`). Affichage : « 🔒 Max » (verrouillé par l'offre) vs « ⏳ Bientôt » (dans l'offre mais pas encore codé). Permet de tout afficher honnêtement et de construire progressivement.

**SIMPLE = outil interne STRICT (décision 🅰️)** — 14 900 FCFA/mois, ≤200 élèves. Seuls **Admin + Enseignants** se connectent. Les **élèves sont des fiches** (pas de login), les **parents n'existent pas**. Contient : élèves/classes/matières, notes/bulletins, présences, emploi du temps, carnet de notes, appel, stats de classe, dashboard, profil, notifications système. PAS de : parents, messagerie, annonces, finance, bibliothèque, QR, surveillance, rapports avancés. Argument d'upsell Pro = « ouvrez l'app à vos élèves ET parents ».

**PRO = engagement familles** — 29 900, ≤1000 élèves. Simple + **portail Parents** (rôle parent + login), **élèves** se connectent, **messagerie & annonces**, **module Finance** (factures/paiements/relances — `billing_admin` + `fees_parent`), bibliothèque, QR, surveillance/discipline, **rapports basiques** (descriptif/instantané : listes, totaux, exports PDF/Excel).

**MAX = groupes & premium** — 59 900, illimité. Pro + multi-établissements, marque blanche (voir [[distribution-and-whitelabel]]), hors-ligne, support dédié, export/API, **analytics avancées** (tendances/comparaisons/prédiction multi-écoles, ≠ rapports basiques Pro), base dédiée.

**Natures de features (effort ≠ uniforme)** : 🟦 module applicatif (rapports, perso, export → on code) ; 🟧 infra (multi-établissement, base dédiée, API, hors-ligne → verrouiller maintenant, gros chantier infra plus tard) ; 🟩 service humain (support dédié → juste afficher le bon canal). **API et analytics avancées = priorité basse** (peu utiles au marché actuel, construire sur demande). **Rapports basiques = à faire tôt** (utile à toutes les écoles Pro).

**PAIEMENT SCOLARITÉ — manuel vs en ligne par offre (décidé juin 2026)** : la facturation a 2 volets. (1) **Suivi manuel/cash** = dans TOUTES les offres y compris Simple (la secrétaire crée une facture + enregistre l'encaissement espèces → statut payé). Implémenté : page admin `admin_billing_page.dart` (createInvoice/recordPayment/deleteInvoice) + table `invoices`/`payments`. (2) **Paiement EN LIGNE (Mobile Money)** = **Pro/Max uniquement** — logique naturelle : en Simple aucun parent/élève n'a de compte pour payer dans l'app. Gating via `onlinePaymentEnabledProvider` (planCode ∈ {pro,max}). Décision user : **construire les pages maintenant même sans agrégateur** → composant `online_payment_sheet.dart` est une **SIMULATION** (choix MTN MoMo/Airtel + numéro → délai + recordPayment method=mtn_momo/airtel_money ref=SIM-*), bandeau « Démo ». Le jour des vrais agrégateurs, seule la confirmation opérateur change. Branché sur `parent_payments_page.dart` (« Payer » + « Tout payer »). ⏳ `student_payments_page.dart` encore 100% mock (tranches en dur, à convertir). Simple → reste manuel ; cas « lien de paiement sans compte » NON tranché.

**ESSAI GRATUIT = offre SIMPLE** (changé de Pro → Simple, juin 2026), 30 jours, sans CB. À l'expiration : retomber en accès très limité (lecture seule du socle) + bannière de réactivation. Inscription crée l'école avec essai Simple. (Demo EAD = essai Simple dans `20260617_subscriptions.sql`.)
