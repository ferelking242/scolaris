Backend Supabase (projet `iaxwvgqusxyhmyansawi`, région Irlande, plan Nano gratuit). Schéma créé directement côté Supabase.

**Baseline versionnée (17 juin 2026)** : `supabase/migrations/20260617_schema_baseline.sql` = 1ʳᵉ source de vérité du schéma, générée par introspection de l'API PostgREST (spec OpenAPI, via la clé service_role) → **63 tables, 132 FK, 9 types enum**. Limites : ne capture PAS les DEFAULT/triggers/RLS/index non-PK/CHECK (pour un dump 100 % fidèle : `supabase db dump` + mot de passe Postgres, non dispo localement — CLI supabase non installée). **Le schéma est très encombré** : ~doublons français/anglais à dédupliquer (`cours`/`courses`, `devoirs`/`assignments`, `paiements`/`payments`, `notes`/`grades`, `annonces`/`announcements`, `ressources`/`resources`, `examens`/`exams`, `groupes_collaboration`/forum_*). Enum `plan_type` = `free/pro/enterprise` → **ne correspond PAS aux 3 offres** Simple/Pro/Max (à aligner pour le module abonnement). Voir [[business-model]].

**Plan d'assainissement (audit 17 juin 2026)** : croisement usage code (`.from()`) × nb lignes → seules **~18 tables** sont actives ; cible propre ~27. `supabase/migrations/20260617_schema_cleanup.sql` = **PASSE 1 prête mais PAS encore exécutée** (à relire + lancer dans SQL Editor) : DROP de 22 tables de modules morts (permissions legacy `roles`/`roles_permissions`/`permission_scopes`, `schedules`/`schedule_slots`, forum/collab, messagerie alt `conversations`, compta `expenses`, + vides), 63→41 tables. **PASSE 2 prête mais PAS encore exécutée** : `supabase/migrations/20260617_schema_cleanup_2.sql` = DROP de 9 doublons FR (`notes`→grades, `cours`/`modules_ue`→courses, `paiements`→payments, `devoirs`/`depot_travaux`→assignments, `examens`→exams, `ressources`→resources, `annonces`→announcements), 41→32 tables (−49 % depuis 63). Sans migration de données (résidus démo, app ne les lit pas).

⚠️ **Corrections importantes de l'audit** : `filieres` est **GARDÉE** (114/115 classes ont `filiere_id` rempli → FK active, pas un doublon de school_series). `student_profiles`/`teacher_profiles`/`user_settings` sont **GARDÉES** : données riches/bien modélisées (matricule, moyenne, rang ; specialisation ; préférences UI) — meilleur design que la table `students` (colonnes FR). Leur adoption = décision d'archi (**passe 3 identité**), pas du nettoyage.

**Identité unifiée (passe 3, 17 juin 2026)** : décision prise = **`users` est LA table unique des personnes** (role student/teacher/parent/admin). Les tables doublons `profiles` et `students` sont **supprimées**. Infos métier dans `student_profiles`/`teacher_profiles`, lien parent↔enfant dans `parent_student`. Toutes les FK `*.student_id` repointées vers `users.id`. Migration : `supabase/migrations/20260617_identity_p3.sql` (repoint FK invoices/attendance/payments/courses/school_classes, DROP profiles+students, trigger `handle_new_user` n'écrit plus dans profiles). Côté code : `SbStudent` gardé comme **façade stable** (prenom/nom dérivés de `users.full_name`) ; `getStudents`/`getStudentById`/jointure `invoices` lisent désormais `users`+`student_profiles`+`classes` (`lib/data/sources/remote/supabase_db_source.dart`). `seed.sql` mis à jour (purge fiches incohérentes + seed EAD cohérent). ⚠️ **Migration + seed PAS encore exécutés** ; à lancer dans SQL Editor puis rebuild app. La démo est multi-écoles (EAD a 6 élèves/4 profs/51 classes en `users`) ; `getStudents` ne filtre pas encore par école → **multi-tenancy à brancher** (passer `schoolId`).

**Multi-tenancy (17 juin 2026)** : isolation par école sur 2 niveaux. **Niveau 1 (app)** : `lib/presentation/providers/db_providers.dart` — nouveau `currentSchoolIdProvider` (lit `AppUser.schoolId`), tous les providers de liste filtrent par `schoolId` (renvoient `[]` si non connecté). **Niveau 2 (RLS)** : `supabase/migrations/20260617_multitenancy_rls.sql` — fonction `current_school_id()` (SECURITY DEFINER, lit users via auth.uid()) + policy `tenant_isolation` sur 25 tables à `school_id` + 3 spéciales (schools via id, attendance via classes, payments via users). `bibliotheque`/`class_levels` = catalogues partagés. ✅ **Exécuté + vérifié** (17 juin 2026) via connexion réelle admin EAD : isolation étanche (EAD voit 51/115 classes, 16/76 users, etc.). ⚠️ Un correctif a été nécessaire : `supabase/migrations/20260617_multitenancy_rls_fix.sql` efface d'ABORD toutes les anciennes policies permissives (`using(true)` héritées qui annulaient l'isolation sur `classes`/`schools` — cumul en OU) puis recrée proprement. **Toujours appliquer le `_fix` après le RLS de base.** Limite restante : isole par école, pas encore d'autorisation intra-école par rôle (un élève pourrait modifier dans sa propre école — couche ultérieure). SQL Editor (postgres) + service_role bypassent la RLS.

**Edge Function `create-account` (A2 — DÉPLOYÉE + vérifiée, 17 juin 2026)** : `supabase/functions/create-account/index.ts`. Crée les comptes côté serveur via l'API admin (clé `service_role` **uniquement** dans la fonction). 2 modes : `create` (nouveau prof/staff → métadonnées role+school_id → trigger crée `public.users`, compte `email_confirm` donc connexion immédiate sans email, tout domaine) ; `link` (login sur fiche existante élève/parent → crée auth SANS school_id pour ne pas déclencher le trigger, puis pose `users.auth_uid` ; rollback si échec). Sécurité : appelant doit être admin/staff, école déduite du profil appelant. **Vérifié en réel** : admin EAD → create role=teacher → `{ok:true}` + ligne users créée. Déployée via Dashboard (Edge Functions). Variables `SUPABASE_*` injectées auto. Côté app : `createMemberAccount` / `enableUserLogin` dans `supabase_db_source.dart` ; B3 (invitation) et B4 (bouton clé « Activer l'accès ») branchés dessus. ✅ **Clé `service_role` retirée de `app_config.dart`** (elle n'était utilisée nulle part dans le client).
